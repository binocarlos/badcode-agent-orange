# Deploying Agent Orange to Kubernetes

A prototype deployment: one namespace, four workloads, no autoscaling, no
backups. It is the compose stack rearranged, not a different architecture.

**Do the local stack first.** `README-stack.md`, one command. Everything here
assumes you already know the thing works.

---

## What runs, and why it is shaped this way

| Workload | What it is |
| --- | --- |
| `agent-orange` (Deployment) | **Two containers in one pod**: a privileged Docker daemon, and agentd |
| `postgres` (StatefulSet) | pgvector — the product layer is Postgres-only |
| `web` (Deployment) | nginx serving a built bundle of `examples/web` |

**The one pod is load-bearing.** In compose, agentd runs with
`network_mode: "service:dind"` — it shares the daemon's network namespace, so it
reaches the daemon on `localhost:2375`, session containers reach agentd back on
the bridge gateway `172.17.0.1`, and the 100-port session pool is addressable.
Containers in one Kubernetes pod share a netns by definition, so this
reproduces compose exactly. Two pods would mean a Service enumerating 100 ports.

**The agentd Service is called `dind`** because `deploy/web.nginx.conf` proxies
to `http://dind:8099`, baked into the web image. The name makes that image run
here unmodified.

**`init-sandbox` is gone.** Compose builds the sandbox image into the daemon at
boot; here the daemon pulls a published one. That is what `base-image` in the
ConfigMap points at.

**One replica, `Recreate`.** Agent Orange is a singleton by design. Two agentds
against one image store would fight over host ports and container ownership.

## Before you start

**1. A registry your cluster can pull from**, and Docker able to push to it.
Being logged into gcloud is *not* enough — Docker resolves credentials per
host, and an Artifact Registry host is a separate entry from the old `gcr.io`
ones:

```sh
gcloud auth configure-docker europe-west1-docker.pkg.dev
```

Skipping this fails the push with `no basic auth credentials`, which reads like
a network problem and is not.

**2. Privileged containers must be permitted.** The Docker daemon needs
`privileged: true` — it manages cgroups, mounts and network namespaces. **GKE
Autopilot refuses this outright**; GKE Standard allows it unless something is
enforcing otherwise. Check yours before building anything:

```sh
kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: dind-probe, namespace: default}
spec:
  containers:
  - name: probe
    image: docker:27-dind
    securityContext: {privileged: true}
EOF
```

`pod/dind-probe created (server dry run)` means you are clear, and nothing was
created. An admission error names exactly what blocked it.

**3. Roughly 500m of CPU and 2GB free**, before any session runs. Each live
session is another container on the same node.

## Deploy

```sh
export REGISTRY=europe-west1-docker.pkg.dev/webkit-servers/agent-orange

# 1. The SESSION base — what a session container runs, and what a project's
#    custom image is built FROM. Prints the tag it used.
./deploy/publish-base.sh

# 2. The SERVICES — Agent Orange itself. Compose builds these locally;
#    Kubernetes cannot build, so they must be pushed.
./deploy/publish-images.sh

# 3. Edit the two files that carry your specifics:
#      deploy/k8s/00-namespace-and-config.yaml   hosts, GCP project, base image
#      deploy/k8s/40-ingress.yaml                the hostname, in both places
#    public-base-url and the Ingress host MUST match — that value is what a
#    session permalink sends a human to.

# 4. Secrets. Not in the repo, and not generated by a script that might get
#    committed with its output.
kubectl create namespace agent-orange
kubectl -n agent-orange create secret generic agent-orange \
  --from-literal=postgres-password="$(openssl rand -hex 24)" \
  --from-literal=database-url='postgres://agentorange:PASTE_SAME_PASSWORD@postgres:5432/agentorange?sslmode=disable' \
  --from-literal=jwt-secret="$(openssl rand -hex 32)" \
  --from-literal=anthropic-api-key='sk-ant-…' \
  --from-literal=test-login='pick-something-unguessable'

# The GCP service account, for GCS blobs and Artifact Registry pulls.
kubectl -n agent-orange create secret generic agent-orange-gcp \
  --from-file=key.json=./secrets/gcp-key.json

# 5. Rehearse, then apply. The dry run exercises every admission controller
#    and writes nothing.
cd deploy/k8s
IMAGE_TAG=<tag from step 2> ./apply.sh --dry-run
IMAGE_TAG=<tag from step 2> ./apply.sh
```

`database-url` repeats the password deliberately: agentd takes a whole URL, and
splitting it into parts to reassemble would be a second place for it to be
wrong.

## Gotchas, in the order they will bite

**The first conversation is slow.** The daemon pulls the session base on the
first session, not at startup. That is the pull, not a hang.

**SSE needs buffering off.** Already set in the Ingress annotations. Without
them the chat appears to hang and then delivers every message at once.

**`AGENTKIT_TEST_LOGIN` is a shared password, not accounts.** Fine behind a URL
nobody knows; swap to `google-client-id` before anyone else uses this. With
*neither* set, agentd falls back to a dev-open mode with **no authentication at
all** — never expose that.

**Nothing here is backed up.** The Postgres volume holds every session, memory
and config event. Cloud SQL is the move when losing it would actually hurt.

**A privileged daemon is a node-level trust boundary.** It runs model-authored
bash, and `docs/02-execution-environment.md` is explicit that plain Docker is
not a safe boundary for untrusted commands when multi-tenant. On a cluster
running anything you care about, that is a real risk and not a theoretical one.

**Sessions hold a container and a host port until deleted or idle.** The
archive sweep reclaims after `AGENTKIT_SESSION_IDLE_TIMEOUT` (default 30m). The
pool is 100, and that is the ceiling on *concurrent* sessions.

## Checking it worked

```sh
kubectl -n agent-orange get pods
kubectl -n agent-orange logs deploy/agent-orange -c agentd | head -40
```

The boot line that tells you which model you are talking to:

```
[agentd] ANTHROPIC_API_KEY unset → MOCK model proxy   # no key reached the pod
```

If you meant to run a real agent and see that line, the secret is not arriving.
If you did *not* mean to bill anything, that line is the one that proves it.
